# Profile photo privacy cutover (not deployed)

The session-safe app changes do not make existing photos private. Keep Storage rules and existing links unchanged until a paired client and migration test passes. Public `viora-media` catalog files are outside this change.

1. Use the exact Expo/Hermes dependency set on a disposable Android preview configured for local emulators or a synthetic test project. Exercise picker, JPEG compression, native Storage transport, profile commit and direct photo read separately. Record the failing stage and sanitized error code, not a URL, token or image. Confirm whether `atob` is available on that runtime before choosing the documented base64 polyfill or a bytes-based uploader.
2. Prototype owner-authenticated `getBytes` with a fixed size cap and verified configured bucket and owner path. Never fall back to a network download URL after an authorization error. Verify owner read, signed-out and cross-account denial, bounded decode, offline failure and account switch while a read completes. Test web and native independently; web may also need CORS configuration.
3. Preserve the active legacy photo until the new-build reader is proven. Map only validated old Storage references for the correct bucket and owner prefix. Inline JPEG legacy photos are currently in the owner/admin-readable profile document. If owner-only is required, migrate the inline data to an owner-only location; do not broaden access or silently remove the user's last good photo.
4. Test replacement with two synthetic objects, failure before and after profile commit, and concurrent replacements. Update the current reference only after the new object is verified. Retire a superseded object only after a guarded proof that it is no longer current and an explicitly approved retention/migration procedure. Old download URLs must be handled separately: a rules change is not a revocation plan. Enumerate known owner prefixes in a dry run, verify current references and issued-link behavior with synthetic objects, then approve migration and rollback criteria before production.
5. Roll out the compatible reader and private writer/rules together with a staged upgrade path for old builds. No destructive production cleanup, rule deployment or link revocation is implied by this draft.
